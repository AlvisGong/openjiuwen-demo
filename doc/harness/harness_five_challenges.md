# 为什么需要 Harness?五个核心挑战

> Harness Engineering 的出现不是空穴来风,而是为了解决五个只有 AI Agent 才会出现的问题。这五个挑战层层递进,从上下文管理到反馈复利,构成了完整的 Harness 工程图景。

---

## 挑战总览

```
挑战一  上下文窗口是易耗品      →  子 Agent 上下文防火墙
挑战二  Agent 无法感知隐式规则   →  仓库是唯一事实来源
挑战三  事后修复远高于事前拦截   →  验证四步流水线 + 预验证
挑战四  模型不可控,需强规则兜底  →  Lifecycle Hooks + 沙箱防护
挑战五  反馈必须产生复利         →  结项沉淀 + 长期记忆闭环
```

---

## 一、挑战一:Agent 的上下文窗口是易耗品

### 问题

这是最容易被忽视的问题。Agent 在"写代码 → 跑测试 → 报错 → 修复 → 再报错"的循环中,每一次失败的日志、diff、工具调用结果都在消耗宝贵的上下文窗口。

### 实证研究

HumanLayer 的研究:18 个主流模型在上下文增长时性能均显著下降,且当上下文中存在低语义相关性的干扰信息时,退化更加陡峭。上下文会随着工作推进而"腐烂"——当膨胀到一定程度,Agent 就进入了所谓的**"笨蛋区"**,即使是简单任务也开始出错。

### 为什么人类不需要担心?

传统软件工程中,上下文管理是人类大脑自动完成的——我们不会因为读了太多代码文件就忘记项目架构。但 LLM 的上下文窗口是一个**有限且会退化的资源**。

### 解法:子 Agent 上下文防火墙

```
父 Agent (高推理模型,如 Opus/Codex)
  ├─ 只做规划、委派、汇总
  │
  ├─→ 子 Agent A (快速模型,独立干净上下文)
  │     └─ 执行具体任务,完成后只返回压缩摘要 + 源引用
  │
  ├─→ 子 Agent B (快速模型,独立干净上下文)
  │     └─ 执行具体任务,完成后只返回压缩摘要 + 源引用
  │
  └─→ 子 Agent C (快速模型,独立干净上下文)
        └─ 在 Git Worktree 中隔离执行,互不干扰
```

**关键设计**:
- 父 Agent 用高推理模型,只做规划、委派、汇总
- 子 Agent 用快速模型,在独立干净的上下文中执行具体任务
- 完成后只返回**压缩摘要 + 源引用**,不污染父上下文
- 子 Agent 在 Git Worktree 中隔离执行,互不干扰

**效果**:可节省 60-70% 的总成本,同时保持代码质量。

### 核心洞察

> 子 Agent 架构不是微服务,不是消息队列,不是任何传统分布式系统概念的翻版。它解决的是一个只有在非人类认知体执行任务时才会出现的问题:**如何在有限的注意力预算内,完成需要无限注意力的工作**。

来源:HumanLayer "Skill Issue: Harness Engineering for Coding Agents"

## 二、挑战二:Agent 无法感知隐式规则

### 问题

同一个项目,昨天的 AI 还记得架构约定,今天开个新会话又全忘了。每次协作都要重新解释一遍背景、分层规则、命名规范。AI 生成的代码能跑,但完全不符合团队规范。

### 典型场景

| 隐式规则              | 人类工程师         | AI Agent        |
|---------------------|-----------------|-----------------|
| "这个模块不能 import 那个包" | 主动问"这样 import 合规吗?" | 直接执行,错了再说   |
| "这个文件应该放在哪个目录?"  | 主动问"放哪合适?"    | 不会问,直接执行     |
| 架构评审会议达成的口头约定    | 记在心里或写在笔记里     | 完全不知道,群聊里读不到 |

**问题本质**:新入职的工程师不熟悉代码库,会主动寻求验证;但 AI Agent 不会,直接执行。

### 为什么"教得更好"有天花板?

- Prompt 写得再好,也没法穷尽代码库的所有隐式规则
- 上下文窗口再大,也装不下整个仓库的架构决策
- 规则会随代码演进变化,你永远追不上
- 规范文档放在群聊或文档库里,AI 读不到
- 依赖 AI 的"常识",不同模型表现差异大,不可靠

### Harness 的思路:让 Agent 自己验证

> 与其教 Agent 怎么做,不如让它自己验证做得对不对。

靠代码、linter、测试来保证正确性,而不是靠 LLM 的"直觉"。这些机械化检查不会出错,不会遗忘,也不会被上下文压缩掉。就像 CI/CD 对人类开发者的作用——自动拦截问题。只不过这次拦截的时机更早,不是合并前,而是**写代码前**。

### 类比:CPU 与操作系统

> CPU 很强大,但没有操作系统它就是一块高速却无方向的芯片——不知道硬盘在哪、网络协议是什么、哪些内存地址可以写。LLM 也一样。它推理能力很强,但它不知道你的 `internal/types/` 不能 import `internal/config/`。**Harness 就是给它装的"操作系统"**。

### 解法:仓库是唯一事实来源

```
不在仓库里的 → Agent 看不见 → 看不见就会违反
       ↓
 把一切编码到仓库中
       ├── 架构决策    → docs/design-docs/xxx.md
       ├── 层级约束    → scripts/lint-deps.py(依赖方向检查)
       ├── 质量规范    → scripts/lint-quality.py(单文件行数、禁止硬编码等)
       ├── 预验证脚本   → scripts/verify_action.py(操作前合法性检查)
       ├── 统一验证入口 → scripts/validate.py(build→lint-arch→test→verify)
       ├── 失败记录    → harness/trace/failures/(结构化保存每次验证失败)
       ├── 项目索引    → AGENTS.md(~100行,只做指路)
       └── 长期记忆    → MEMORY.md(截断到 200 行)
```

### AGENTS.md 的设计原则

> AGENTS.md 是**地图,不是手册**。

- 控制在 ~100 行,只做索引和指路
- 详细内容放在 `docs/` 目录里**按需加载**
- 要改 auth 模块?先读 AGENTS.md 找到路,再读 `docs/design-docs/auth.md` 拿细节
- 用不上的文档根本不加载
- 保持短小精悍还有一个好处:**不容易腐烂**,巨大的指令文件会迅速过时

### 核心洞察

这呼应了 Karpathy 在 LLM Wiki 模式中的核心洞察:**知识必须跟着代码一起走**。新人 clone 仓库就能拿到全部上下文,Agent 打开项目就能读到一切。

来源:Qoder 工程实践:Harness Engineering 指南

## 三、挑战三:事后修复的成本远高于事前拦截

### 问题

重点不是事后检查,而是**事前预防**。Agent 通常的工作流是写代码、跑测试、发现错误、修复、再跑测试。当一个层级违反在 50 行代码写完后才被 linter 抓到,修复代价很大——撤销改动、重新设计,差不多要消耗 10 次 tool call。

而如果在写代码前先问一句"这样做合法吗",两次交互就够了。

### 3.1 验证四步流水线

```
build → lint-arch → test → verify
  │        │         │       │
  │        │         │       └─ 端到端功能验证
  │        │         └─ 单元/集成测试
  │        └─ 架构和质量合规
  └─ 代码能否编译
```

| 阶段         | 作用                   |
|------------|----------------------|
| build      | 编译都不过就别往下走了     |
| lint-arch  | 架构约束,依赖方向检查      |
| test       | 功能正确性              |
| verify     | 端到端功能验证——不是"函数返回值对不对",而是"用户操作完,最终结果对不对" |

### 3.2 预验证模式

```bash
python3 scripts/verify_action.py --action "create file internal/types/user.go"
# ✓ VALID: internal/types/ is Layer 0, user.go follows naming convention

python3 scripts/verify_action.py --action "import internal/core from internal/handler"
# ✗ INVALID: internal/handler (L4) cannot import internal/core (L3)
```

**什么时候需要预验证?**

不是每个操作都需要。改个函数体不需要,加个测试文件也不需要。但只要涉及:
- "在新位置创建文件"
- "添加跨包 import"

就该先验证。**层级违反是 Agent 翻车的头号原因**。

### 3.3 验证失败怎么办?

验证挂了之后,会自动进入修复循环——分析错误、改代码、重新跑验证,一般 1-3 轮就收敛。

```
验证失败 → 分析错误 → 改代码 → 重新验证
              ↑                    ↓
              └──── 1-3 轮收敛 ────┘
                      ↓
            同一错误转 3 圈还没过 → 停下来交给人
```

**为什么 3 轮就停?** 不是它一定修不好,而是再转下去上下文窗口就要爆了。

### 3.4 踩过坑的经验

- **故意引入违规来测试 lint**:加一个跨层 import 确认能被检测到,如果 lint 没报错说明护栏是纸糊的
- **永远不要禁用 lint 规则来"解决"问题**:应该改代码而不是改规则
- **测试不需要每次跑全量**:支持只跑受影响的包,速度快很多

来源:Qoder 工程实践:Harness Engineering 指南

## 四、挑战四:模型不可控,需要强规则兜底

### 核心原则

> LLM 不擅长数标签、对正则。能用确定性程序判定的,不要让 LLM 判。

### 程序化校验 vs LLM 语义校验

| 维度       | 程序化校验          | LLM 语义校验      |
|----------|-----------------|-----------------|
| 工具       | HTMLParser       | LLM-as-Judge    |
| 方法       | 正则匹配            | 事实对齐分析         |
| 深度       | AST 分析          | 意图理解           |
| 决策       | 规则引擎            | 语义判断           |
| 响应速度     | 毫秒级             | 慢但深入           |
| 准确率      | 零假阳性            | 高准确率           |
| Token 消耗 | 零               | 消耗 Token         |

**两层分工明确**:程序化校验负责结构完整性问题,毫秒级响应、零假阳性;LLM 语义校验负责事实对齐、意图理解,慢但深入。token 效率和准确率都更高。

**实际案例**:
- 网页里多写了或漏写了 HTML 标签(如多写的 `</div>` 闭合标签)→ 程序化校验自动发现
- "优于市场 85%"这类夸大宣传 → 拿 HTML 和数据源做对比,LLM 事实校验才能发现

### Lifecycle Hooks:在关键时机插入强规则

> 不在推理循环里硬编码逻辑,而是在关键节点挂 Hook 做拦截、注入、记录——既保留模型自主推理的灵活性,又能施加确定性工程约束。

| Hook            | 时机     | 作用                              |
|-----------------|--------|---------------------------------|
| PreReasoning    | 推理前   | 注入最新上下文,把最新 State、预加载记忆注入 system prompt |
| PreToolCall     | 工具调用前 | 安全拦截,校验能力边界、检查幂等键、判断风险等级     |
| PostToolCall    | 工具调用后 | 结果校验与状态更新,对照实时业务数据交叉验证        |
| PostReasoning   | 推理后   | 幻觉检测,验证输出是否与真实数据一致            |
| OnSessionEnd    | 会话结束   | 记忆回写,提炼场景轨迹事件写入记忆文件           |

**Hook 的妙处**:把"安全""可观测""持续演化"这些横切关注点从业务逻辑里彻底解耦出来,统一收敛到框架层管理。

### 沙箱防护:把"不可信代码"关在隔离边界内

#### 安全硬约束

- 容器以非特权用户运行,根文件系统只读
- CPU 限额不超过 50%、进程数上限不超过 64
- 网络默认禁止所有出站连接,仅按最小化 allowlist 放行
- 系统调用通过白名单收敛,禁用高危调用
- 绝不向沙箱注入任何宿主机环境变量

#### 执行约束

- 工具层强制 timeout 上限,且 Agent 传入的 timeout **只能缩小不能放大**
- stdout、stderr 设大小上限(64KB),超出即截断
- 所有执行记录完整写入审计日志,既能事后追溯定责,也为模型优化沉淀数据

来源:
- Harness Engineering: C 端 AIGC 内容生产自优化实践
- 更可靠的主播助理:淘宝主播 Agent 的 Harness 工程实战

## 五、挑战五:反馈必须产生复利

### 问题

> 这是 Harness Engineering 最容易被忽视、却最能拉开差距的一层。反馈学习层要回答的是**"下次能不能更好"**。

Agent 在澄清里问错了什么、方案里漏看了什么、CR 里反复被指出什么——如果只留在聊天记录里,需求结束就蒸发了。下一个需求大概率还会再犯一次。

### 5.1 为什么留痕比沟通更重要

CR 评论和 issue 对话不只是当次需求的协作工具,更是**结项沉淀的素材**。哪些澄清反复出现、哪些代码模式被反复指出、哪些人工介入本可以自动化——这些信息只有留在平台上,结项时才能被系统性地回看和分析。

**落地方式**:分支创建、CR 评论读写、milestone 回刷都通过平台完成。锚定已有协作平台,是因为它本身已有钉钉群绑定和状态推送——Agent 做评论和回刷,团队在钉钉群里就能直接收到通知,不需要额外关注新的渠道。

### 5.2 结项沉淀三问

结项不是写一句"已完成"。它的核心是回看整个需求过程,回答三个问题:

```
┌──────────────────────────────────────────────────────┐
│  结项沉淀三问                                          │
├──────────────────────────────────────────────────────┤
│                                                      │
│  Q1: 哪些知识是稳定的?                                 │
│  A:  业务规则、系统边界、验收规范、排障经验              │
│  →   这些是下一个类似需求不需要重新学的东西              │
│  →   稳定知识通过 CR 确认后进入长期 wiki 和 codemap      │
│                                                      │
│  Q2: 哪些流程可以改进?                                 │
│  A:  Agent 在哪个环节犯了错、走了弯路、被人工反复纠正     │
│  →   这些是 skill 和提示词的迭代候选                    │
│  →   如果某个问题在多次需求里反复出现,就不应该继续靠人盯着│
│                                                      │
│  Q3: 哪些材料只需要归档?                               │
│  A:  一次性的实现细节、临时调试记录、中间状态            │
│  →   不需要进入长期知识,留在归档里作为审计底稿          │
│                                                      │
└──────────────────────────────────────────────────────┘
```

### 5.3 闭环的意义

这个设计完成后,闭环才真正合上:

```
结项蒸馏出的稳定知识
       ↓
回到长期 wiki
       ↓
成为下一个需求进入时的背景知识来源
       ↓
每做一个需求,Agent 理解业务的基线就高一点
       ↓
人需要解释的上下文就少一点
       ↓
系统从"无状态"走向"有复利"
```

> **没有这一层,系统就是无状态的——每个需求都得从零开始。有这一层,每次执行都在为下一次积累优势。**

## 六、五大挑战的内在逻辑

```
挑战一  上下文是易耗品
       ↓ 解法:子 Agent 隔离
挑战二  隐式规则无法穷尽
       ↓ 解法:仓库即事实来源
挑战三  事后修复成本高
       ↓ 解法:事前预验证 + 四步流水线
挑战四  模型不可控
       ↓ 解法:Lifecycle Hooks + 沙箱
挑战五  反馈必须复利
       ↓ 解法:结项沉淀 + 长期记忆闭环
       ↓
完整 Harness:从"能用 Agent"到"驾驭 Agent"
```

五个挑战层层递进:
1. **上下文管理**(空间维度):解决注意力预算问题
2. **规则感知**(知识维度):解决隐式规则不可见问题
3. **验证拦截**(时间维度):解决事前预防问题
4. **强约束**(控制维度):解决模型不可控问题
5. **反馈复利**(演化维度):解决系统能否进化问题

## 七、对应到 ETCSV 治理模型

| ETCSV 组件                 | 五大挑战的对应                    |
|---------------------------|------------------------------|
| **E** Execution Loop      | 挑战一的子 Agent 隔离执行           |
| **T** Tool Registry       | 挑战四的工具能力边界校验              |
| **C** Context Manager     | 挑战一的上下文防火墙 + 挑战二的按需加载   |
| **S** State Store         | 挑战五的长期记忆与结项沉淀            |
| **L** Lifecycle Hooks     | 挑战四的五大 Hook + 挑战三的预验证拦截  |
| **V** Evaluation Interface | 挑战三的四步流水线 + 挑战四的程序化校验  |

DeepAgent 的 ETCSV 六大组件,正是这五大挑战的工程化落地。

## 八、一句话总结

**Harness Engineering 的五大挑战——上下文易耗、规则隐式、修复昂贵、模型不可控、反馈易蒸发——每一个都是只有 AI Agent 才会出现的全新问题。** 它们的解法共同构成了从"能用 Agent"到"驾驭 Agent"的完整工程框架:用子 Agent 隔离管上下文,用仓库编码管规则,用预验证管质量,用 Hook 和沙箱管行为,用结项沉淀管演化。这五层加在一起,才是 Harness Engineering 的完整图景。
