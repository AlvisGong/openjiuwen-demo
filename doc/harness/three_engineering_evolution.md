# 三种工程的演进:Prompt → Context → Harness

> Harness Engineering(驾驭工程)的出现,是 AI 驾驭系统开始成形的信号。但提到驾驭工程,不得不回顾提示词工程和上下文工程。

---

## 一、演进脉络总览

```
Prompt Engineering       Context Engineering       Harness Engineering
(提示词工程)              (上下文工程)               (驾驭工程)
─────────────           ─────────────             ─────────────
怎么跟模型说话?    →     模型应该看到什么?    →     整个环境应该如何运作?
                                                                  
用户精心雕琢指令          Builder 构建动态系统         用户设计完整运行环境
                                                                  
单次交互、无状态          每一步提供恰当上下文          约束、反馈、验证、治理
                                                                  
大师手艺                  工程化系统                   环境治理
                                                                  
2022-2023                 2024-2025                   2025+
```

**核心演进**:人类角色从"说话者"→"构建者"→"驾驭者",关注点从"说什么"→"看到什么"→"环境如何运作"。

---

## 二、提示词工程 Prompt Engineering

### 核心问题
**怎么跟模型说话?**

### 人类角色
用户精心雕琢每一句指令的措辞、格式、示例,试图从黑盒中诱导出正确答案。

### 典型技术
- Few-shot Learning(少样本学习)
- Chain-of-Thought(思维链)
- 角色扮演(Role-Playing)
- 格式化输出指令
- 负面提示(Negative Prompting)

### 本质
在一个**固定的对话窗口**里做文章。把模型当黑盒,通过输入侧的精心设计,诱导出期望的输出。

### 局限性
- **单次交互**:每次对话独立,无状态延续
- **无状态**:上一轮的经验无法沉淀到下一轮
- **高度依赖个人经验**:更像大师手艺,而非工程
- **脆弱性**:提示词稍改几个字,结果可能天差地别
- **不可复现**:不同模型、不同版本对同一提示词响应不同

### 适用场景
- 单轮 QA、文本生成
- 快速原型验证
- 模型能力探索

---

## 三、上下文工程 Context Engineering

### 核心问题
**模型应该看到什么?**

### 人类角色
角色从**用户**转化为 **Agent Builder**。Builder 们系统性地设计、构建并维护一个动态系统,在 Agent 执行任务的每一步为其提供恰当的上下文。

### 典型技术
- **知识库集成**:RAG 检索增强
- **工具调用**:Function Calling、MCP
- **记忆管理**:短期记忆、长期记忆、工作记忆
- **动态上下文组装**:根据任务阶段注入不同上下文
- **上下文压缩与摘要**:防止上下文膨胀

### 关键转变
关注点从**用户应该说什么**转向 **Builder 们让模型看到什么**,从而让模型更懂用户。

### 里程碑
2025 年 6 月,Andrej Karpathy 明确表态:
> **上下文工程比提示工程重要得多。**

这句话标志着行业共识的形成:与其雕琢单句指令,不如构建动态上下文系统。

### 局限性
- **仍聚焦于"输入侧"**:优化模型看到什么,但不管模型输出后会发生什么
- **缺乏环境约束**:模型可以"看到"很多,但没有"不能做什么"的边界
- **无执行治理**:上下文准备好了,但执行过程仍可能跑飞
- **无反馈闭环**:模型输出后,环境无法自动验证、纠正

### 适用场景
- 多轮对话 Agent
- RAG 知识库应用
- 工具增强 Agent

---

## 四、驾驭工程 Harness Engineering

### 核心问题
**整个环境应该如何运作?**

### 人类角色
角色再次从 **Agent Builder** 手里交还到**用户**手里(注意:这里的"用户"是设计环境的架构师角色)。

通过设计**完整的运行环境**,包括:
- **约束(Constraints)**:模型不能做什么
- **反馈回路(Feedback Loops)**:输出后如何反馈
- **自动验证(Auto Verification)**:如何判断输出对错
- **熵管理(Entropy Management)**:如何控制不确定性
- **生命周期治理(Lifecycle Governance)**:任务如何开始、进行、结束

### 典型技术
- **Execution Loop**:思考-行动-观察主循环
- **Tool Registry**:工具能力边界定义
- **Context Manager**:上下文质量与体积维护
- **State Store**:持久化运行状态,支持中断恢复
- **Lifecycle Hooks**:关键时机插入强规则拦截
- **Evaluation Interface**:可观测、可分析的评估体系

### 核心特征
| 特征       | 说明                                       |
|----------|------------------------------------------|
| 环境治理   | 不只管输入,管整个执行过程                     |
| 反馈闭环   | 输出 → 验证 → 修正 → 再输出                  |
| 熵管理     | 主动控制不确定性,而非被动承受                 |
| 约束落地   | 用代码强制规则,而非靠模型自觉                 |
| 可中断恢复  | 长任务可暂停、可回放                         |

### 适用场景
- 长时序、多步骤复杂任务
- 高风险场景(需要约束和验证)
- 多 Agent 协作编排
- 生产级 Agent 系统

## 五、三者对比

| 维度        | Prompt Engineering | Context Engineering | Harness Engineering |
|------------|--------------------|--------------------|--------------------|
| **核心问题**  | 怎么说话?           | 模型看什么?         | 环境怎么运作?        |
| **人类角色**  | 用户                | Agent Builder      | 环境架构师           |
| **关注点**   | 输入措辞             | 输入上下文           | 整个执行环境          |
| **状态**     | 无状态              | 动态上下文           | 持久化状态 + 中断恢复  |
| **反馈**     | 无                  | 被动(下一轮看到结果) | 主动(自动验证 + 修正)|
| **约束**     | 靠提示词建议         | 靠上下文暗示         | 靠代码强制           |
| **不确定性**  | 被动承受             | 部分缓解             | 主动治理(熵管理)    |
| **复现性**   | 低                  | 中                  | 高                  |
| **工程化程度**| 手艺                | 系统                | 治理框架             |
| **代表时间**  | 2022-2023          | 2024-2025          | 2025+              |

## 六、演进的本质:从"影响模型"到"治理系统"

### 三次跃迁

```
[提示词工程]     影响"模型这一刻的输出"
     ↓
[上下文工程]     影响"模型在整个任务中看到的信息"
     ↓
[驾驭工程]       治理"模型 + 工具 + 环境 + 反馈"的完整系统
```

### 每次跃迁解决了什么

| 跃迁              | 解决了上个范式的什么痛点              |
|-----------------|---------------------------------|
| Prompt → Context | 单次交互无状态 → 多轮动态上下文         |
| Context → Harness | 只管输入不管执行 → 全流程环境治理       |

### 核心洞察

- **提示词工程**:把模型当黑盒,雕琢输入
- **上下文工程**:把模型当白盒,精心喂食
- **驾驭工程**:把模型当"马",修建跑道、设护栏、装仪表盘

驾驭工程不是替代前两者,而是**包抄前两者**——在提示词和上下文之外,加上约束、反馈、验证、治理,形成完整的"驾驭"能力。

## 七、与 DeepAgent 的关系

DeepAgent 的 harness 设计正是**驾驭工程**的典型实现:

| 驾驭工程要素        | DeepAgent 对应                    |
|-----------------|----------------------------------|
| Execution Loop  | Runner.runAgentStreaming 主循环    |
| Tool Registry   | registerHarnessTool + LocalFunction|
| Context Manager | ProgressiveToolRail 工具过滤       |
| State Store     | Session 状态持久化                 |
| Lifecycle Hooks | DeepAgentRail.beforeModelCall 等  |
| Evaluation Interface | markitdown + subagent QA 闭环 |

DeepAgent 的 ETCSV 六大组件,就是驾驭工程六大要素的具体落地。

---

## 八、一句话总结

**提示词工程雕琢输入,上下文工程构建信息流,驾驭工程治理整个执行环境。** 三者不是替代关系,而是包抄关系——每一层都建立在前一层之上,逐步把"与模型对话"从手艺升级为系统工程,再升级为治理框架。Harness Engineering 的出现,标志着 AI 系统从"会用模型"走向"驾驭模型"。
