# 三类核心资产的"逻辑统一、物理分治"存储设计

## 一、设计总纲

主播 Agent 的三类核心资产分别存放在三个独立的基础设施上,各取所长,**不硬扛**。

## 二、资产与存储映射

| 资产类型 | 物理存储 | 选型理由 | 读写特征 |
|---------|---------|---------|---------|
| **会话信息**(session/场次/运行时消息/Checkpoint) | **MySQL** | 强一致、点查高效、按 session_id/live_id 精确加载 | 在线频繁读写、状态持久化 |
| **记忆**(主播画像/事实记忆/行为记忆/记忆片段) | **Hologres** | 原生支持向量+全文+标量混合检索,满足多路召回 | 在线高频检索、异步写入 |
| **技能 Skill** | **GitLab** | 代码化维护,支持版本管理、Code Review、预检校验、灰度发布 | 离线维护、发布时加载 |

## 三、三大资产的存储底座

### 1. 记忆存 Hologres:向量+全文+标量三位一体

每条记忆片段包含:
- **内容原文** → 支持全文检索
- **内容向量** → 支持语义检索
- **JSONB 元数据** → 记忆类型/目标实体/来源平台设备/信任分/使用采纳次数等标量,支持精确过滤

借助 Holo 的向量索引做混合检索,Agent 既能"按语义找相关记忆",又能"按主播 ID/场次/平台精确过滤"。

### 2. 技能存 GitLab:代码化版本管理

Skill 本质是**带 Schema 约束、能力域声明和校验规则的代码资产**,天然适合 Git 维护:
- 能力声明、参数 Schema、风险规则全部纳入版本管理
- 新 Skill 上线前走预检平台校验 + Code Review
- 通过灰度发布上线

### 3. 会话存 MySQL:共享存储支撑多副本对等

- 表:`agent_session`
- 索引:`user_id + session_id + state_key`
- 一个 `state_key` 对应一类状态(会话基础信息/场次信息/原始消息/运行时消息/卸载上下文/压缩事件/Plan 规划等)
- **按需点查加载**,运行过程中动态取用

关键设计:**状态全部落在 MySQL 共享存储,而非副本本地内存** → Agent 才能做到多副本对等部署、跨节点状态一致、服务不中断。

## 四、设计收益:"逻辑统一、物理分治"

### 收益 1:负载分治,各取所长

检索密集的记忆走 Holo、版本化的技能走 GitLab、强一致的会话走 MySQL——**没有用一套存储硬扛所有负载**。

### 收益 2:语义接口屏蔽底层差异

框架层把三套后端封装在**统一的工作区抽象**之后,Agent 业务逻辑只面向语义接口:

```
加载上下文 / 读写记忆 / 调用技能 / 持久化状态
```

**不感知底层是 Holo 还是 MySQL**,存储演进也不会反向冲击业务代码。

## 五、一句话总结

**三类资产(会话/记忆/技能)对应三种存储(MySQL/Hologres/GitLab),各取所长——会话强一致、记忆多路召回、技能版本化;框架层用统一工作区抽象屏蔽底层,业务代码只面向语义接口,实现"逻辑统一、物理分治"。**
