# Harness 驾驭工程是 AI 平权的必经之路

> 核心命题:OpenClaw 将 AI 主权从模型厂商转移到用户手中,但调教 AI 并不简单——这一背景加速了 Harness 驾驭工程的市场共识。**Harness 一词来源于马具:马是强大的 AI 模型(黑盒、不可控);Harness 是缰绳、马鞍和护具(工程管理学);骑手是人类工程师(明确意图、设计环境、构建反馈回路)。**

## 一、引爆点:客厅里来了一条龙

### OpenAI 的惊人实验

2026 年 2 月,OpenAI 发布《Harness Engineering: Leveraging Codex in an Agent-First World》:3 名工程师(后扩展到 7 人)在 5 个月内用 Codex Agent 生成**超 100 万行生产级代码**,合并约 **1500 个 PR**,**没有一行代码是人类手写的**。

### 龙的隐喻

> 我们的客厅里来了一条龙。它聪明、强大,目前看起来还算温顺。但龙会长大,我们需要的不是更粗的铁链,而是一套完整的驾驭系统——缰绳、马鞍、护具,以及一个懂得如何与龙共处的骑手。

## 二、工程演进:提示词 → 上下文 → 驾驭

### 三次革命的"驾驭"对照

| 革命 | 释放的力量 | 驾驭工具(Harness) |
|------|-----------|------------------|
| **工业革命** | 物理力量(蒸汽机) | 飞轮调速器、安全阀、传动系统 |
| **信息革命** | 计算力量(计算机) | 操作系统、编程语言、软件工程方法论 |
| **AI 革命** | 认知力量(LLM) | Harness Engineering = AI 时代的操作系统 + 软件工程方法论的统一体 |

### 三种工程的演进谱系

| 工程 | 核心问题 | 人类角色 | 作用范围 |
|------|---------|---------|---------|
| **提示词工程** | 怎么跟模型说话? | 用户雕琢每一句指令(Few-shot/CoT/角色扮演) | 固定对话窗口内做文章,单次交互、无状态,**更像大师手艺而非工程** |
| **上下文工程** | 模型应该看到什么? | Agent Builder 系统性设计动态系统(知识库/工具/记忆) | 从"用户应该说什么"转向"Builder 让模型看到什么" |
| **驾驭工程** | 整个环境应该如何运作? | 用户设计完整运行环境(约束/反馈回路/自动验证/熵管理/生命周期治理) | 从 Builder 交还到用户 |

> **2025 年 6 月,Andrej Karpathy 明确表态:上下文工程比提示工程重要得多。**

**核心洞察**:驾驭工程引发共鸣,与 OpenClaw 促使 **AI 主权从模型厂商转移到用户侧** 紧密关联。权责对等——拥有了调试 Agent 的权利,也需要学会 Harness,懂得和 Agent 相处。

## 三、4 个案例:Harness 不是软件工程的重新包装

### 案例一:一个编辑工具的改变,让 15 个模型同时变强

**来源**:Can Duruk, "I Improved 15 LLMs at Coding in One Afternoon", 2026.02

**问题**:Agent 修改代码文件的编辑工具本身是巨大失败源。Grok 4 使用 patch 格式失败率高达 **50.7%**。

| 编辑方式 | 缺陷 |
|---------|------|
| OpenAI apply_patch | 要求模型生成特定格式 diff |
| Claude Code str_replace | 要求模型精确复现旧文本每个字符 |
| Cursor 专用 70B 合并模型 | 训练成本高 |

**Hashline 方案**:每行附 2-3 字符内容哈希标签,模型编辑时引用标签而非复现原文。

**结果**:16 个模型、3 种编辑工具、180 个任务。Grok Code Fast 1 成功率从 **6.7% → 68.3%**(十倍提升),Grok 4 Fast 输出 token 下降 **61%**。

> **"你在怪飞行员,但问题出在起落架上。"** — 模型表达意图的接口设计直接决定它能否把正确想法变成正确代码。

### 案例二:技术债的指数级放大效应

**来源**:AgentsMesh 开发者, "52 Days, 350K Lines Solo", Reddit, 2026.03

**发现**:52 天 35 万行代码中,Agent 会把临时妥协(绕过 Service 层直查 DB、硬编码魔法数字)当作"先例",下次系统性复用。

| 维度 | 传统软件工程 | Agent 协作开发 |
|------|------------|--------------|
| 累积方式 | 线性(受限于团队规模和 code review) | **指数级(自我复制的病毒)** |
| 传播速度 | 几天到几周 | **几小时内复制到代码库每个角落** |
| 好的实践 | 被模仿 | 被放大 |
| 捷径 | 被规避 | **被放大** |

**OpenAI 的解法**:把"品味"编码为自动化规则
- 倾向共享实用程序包,集中管理不变式
- 验证边界/依赖类型化 SDK,不 YOLO 探测数据
- 定期运行后台 Codex 任务扫描偏差、更新质量等级、发起重构 PR(大多 1 分钟内审查自动合并,功能类似垃圾回收)

> **技术债务就像高息贷款:不断小额偿还,总比累积后痛苦一次解决要好。人类的品味一旦被捕捉,就会持续应用于每一行代码。**

### 案例三:子 Agent 作为"上下文防火墙"

**来源**:HumanLayer, "Skill Issue: Harness Engineering for Coding Agents", 2026.03

**问题**:Agent 上下文窗口随工作推进"腐烂",每次工具调用/文件读取/grep 结果都留下残留,膨胀到一定程度进入"**笨蛋区**"。

**实证**:18 个模型在 Terminal Bench 2.0 上表现随上下文长度增加显著下降,低语义相关性干扰信息存在时退化更陡峭。

**解法**:子 Agent 作为上下文防火墙

| 角色 | 模型 | 职责 | 上下文策略 |
|------|------|------|-----------|
| **父 Agent** | 昂贵高推理模型(如 Opus) | 规划和编排 | 始终保持在"聪明区",跨数十子任务维持连贯性 |
| **子 Agent** | 便宜快速模型(如 Sonnet) | 隔离上下文中执行具体任务 | 只返回高度压缩结果 + 源引用,中间过程不污染父 Agent |

> **这是全新架构模式,不是微服务/消息队列/传统分布式概念的翻版。它解决的是只有非人类认知体才有的问题:如何在有限注意力预算内,完成需要无限注意力的工作。**

### 案例四:反馈回路的重新设计

**来源**:HumanLayer + LangChain "Improving Deep Agents"

**HumanLayer 的反直觉原则**:

> **"成功应该是沉默的,只有失败才应该发出声音。"**

早期错误:每次 Agent 改代码后跑完整测试套件,4000 行测试输出涌入上下文,Agent 对测试文件产生幻觉,丢失任务追踪。

**解法**:Hook 脚本在 Agent 停止时自动跑格式化 + TypeScript 检查——通过则完全静默(不注入任何内容),失败则只输出错误信息并重新激活 Agent。

**LangChain 的两个中间件**:
- `PreCompletionChecklistMiddleware`:Agent 试图交卷时拦截,强制对照任务规格验证
- `LoopDetectionMiddleware`:追踪对同一文件的重复编辑,N 次后注入"也许你该换个思路"

**结果**:LangChain 编码代理在 Terminal Bench 2.0 从前 30 名跃升至**前 5 名**。

| 维度 | 传统 CI/CD(为人类设计) | Agent 反馈回路 |
|------|---------------------|--------------|
| 测试报告 | 越详细越好 | 信息量精确控制 |
| 成功信号 | 完整报告 | **压缩到零(静默)** |
| 失败信号 | 详细堆栈 | **精炼到最小可操作单元** |
| 循环检测 | 无 | **N 次重复编辑后提示换思路** |
| 强制验证 | 无 | **交卷前强制对照需求检查** |

> **同一个模型,不同的 Harness,截然不同的结果。Agent 竞争优势不仅在你用了哪个模型,更在于你构建了怎样的 Harness。Harness 成了护城河——不只是 Agent Builder 们的护城河,更是 Agent User 们的护城河。**

## 四、群体智能:企业业务创新的拐点

> 提效的故事已经不够性感,**业务创新**才是企业为 Token 付费的最强动力。Harness Engineering 不仅让单 Agent 更可靠,更优化多 Agent 协作,通过**群体智能**加速业务创新——克服岗位间知识孤岛、跨岗位协作创意衰减。

### CLI-Anything:群体智能的基础设施

**来源**:香港大学数据智能实验室(HKUDS)

**痛点**:AI Agent 能推理、写代码、搜索,但让它打开 GIMP 去背景、用 Blender 渲染 3D 场景?做不到——GUI 是为人类设计的,不是为 Agent 设计的。

**方案**:Claude Code 插件,分析任意软件源代码,自动生成生产级 CLI,调用真实应用后端(LibreOffice 生成 PDF、Blender 渲染 3D、Audacity 处理音频)。

**7 阶段全自动流水线**:分析→设计→实现→测试→文档→发布,输出可 pip install 的 Python 包。

**关键**:每个 CLI 自带 `SKILL.md`(机器可读能力描述文件)→ Agent 运行时自动发现其他 Agent 能做什么,动态组建协作关系。

### HiClaw:群体智能的操作系统

**来源**:阿里云

**单体架构 OpenClaw 构建群体智能的四大问题**:

| 问题 | 说明 |
|------|------|
| 可扩展性差 | 无法自由组合,需运维/AI 中台重新部署 |
| 模型不自由 | 所有 Agent 只能用默认模型,无法替换对比 |
| 越聊越贵、效果越差 | 多 Agent 在一个房间协作,记忆越长、Skills 越多越被污染 |
| FinOps 难落地 | Token 消耗不可控,ROI 面临挑战 |

**HiClaw 的四大设计**:

| 设计 | 解决的问题 |
|------|-----------|
| **Manager-Workers 架构** | 灵活创建角色 Worker,引入企业自建 Agent,Skills 和记忆独立存储避免污染 |
| **每个 Agent 支持自定义** | OpenClaw/Copaw/NanoClaw/ZeroClaw/企业自建,自由配置后端模型(代码用百炼 Coding Plan、文本用本地 Qwen),助力 FinOps |
| **MinIO 共享文件系统** | Agent 间信息共享,大幅降低多 Agent 协作的 Token 消耗 |
| **Higress AI Gateway** | 鉴权路由/凭证安全/后端稳定(多模型 fallback/限流降级)/Skills 统一管理/入口监控/安全审计 |

**实践案例**:汽车生产商计划生产 700w 豪车,设计 N 个角色进行 100 轮讨论,从品牌认知、舒适需求、安全隐私、品牌社交、软价值等多方面激烈讨论,给出结果。

> **Harness Engineering 是让企业拥有一支可编排、可治理、可持续进化的数字化智能团队。个人效率提升是线性的,而群体智能的涌现是指数级的。**

## 五、一句话总结

**Harness 驾驭工程是 AI 平权的必经之路——OpenClaw 把 AI 主权从模型厂商转移到用户侧,权责对等要求用户学会 Harness。从提示词工程(怎么说话)→ 上下文工程(看到什么)→ 驾驭工程(整个环境如何运作),这是从手艺到系统再到生态的三级跃迁。4 个案例证明:编辑工具设计(Hashline 让 15 个模型同时变强)、技术债指数级放大(品味编码为自动化规则)、子 Agent 上下文防火墙(有限注意力预算内完成无限注意力工作)、反馈回路重新设计(成功沉默、失败发声)——同一个模型不同 Harness 截然不同结果。CLI-Anything 和 HiClaw 把 Harness 推向群体智能:个人提效是线性的,群体智能涌现是指数级的。**
