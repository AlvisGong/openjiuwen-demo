# Harness 工程实践:主播 Agent 的八大核心能力

> 让 Agent 在直播场景"看得清、调得稳、防得住、规划远、测得准"

## 一、上下文工程:让模型"看得清、记得住、不漂移"

**对抗两堵墙**:上下文膨胀(Token 耗尽、延迟飙升、成本失控)+ 注意力漂移(关键信息淹没)。

### 三大手段

| 手段 | 做法 | 价值 |
|------|------|------|
| **分层压缩** | 3 层压缩(历史工具调用/历史对话轮次/当前轮次)+ Session 级话题分段(打场景标签 pre-live/on-live/post-live) | 控制体积,保留可回溯结构 |
| **Reducer 模式更新状态** | LLM 只决策(产 Action),Reducer 纯函数变更 State;每轮把最新 State 快照注入 system-hint | 解决状态模糊/上下文膨胀/不可回放三大问题 |
| **大上下文卸载** | 大结果卸载到 OSS/Tair(路径 id + 预览);需提取→沙箱 shell 过滤,需摘要→工具返回摘要 | 把"不必时刻在场"的内容外置 |

**Reducer 模式是核心创新**:替代"工具 JSON 结果一股脑塞历史"的传统做法,模型每轮看到的是**干净、确定、最新的状态快照**。

## 二、工具调用:能力边界、强约束与错误恢复

### 三层强化

1. **能力边界声明** — Skill 注册时声明能力范围,调用前校验是否越权;新 Skill 上线走预检平台
2. **Schema 强约束 + 幂等设计** — JSON Schema 约束参数结构;有副作用写操作必须带幂等键(UUID),框架层去重校验,杜绝"双切品""双改价"
3. **结构化错误码 + 自动修复**

| 错误码 | 类别 | 框架行为 |
|--------|------|---------|
| 3xxx | 业务异常(越界/权限不足) | 解析 AI 友好信息,换策略重试 |
| 4xxx | 参数异常 | 框架自动修复参数后重试 1 次 |
| 5xxx | 系统异常(超时/不可用) | 自动重试,最多 3 次,指数退避 |
| 9xxx | 不可恢复异常 | 不重试,Hook 通知主播 |

## 三、生命周期 Hook:在关键时机插入强规则

**设计哲学**:不改写模型推理循环,而是在关键时机插入钩子,做拦截/注入/记录。

| Hook 时机 | 职责 |
|-----------|------|
| **PreReasoning** | 注入最新 State + 按需加载场景记忆到 system prompt |
| **PreToolCall** | 安全拦截:能力边界/幂等键/风险等级审批 |
| **PostToolCall** | 结果校验 + 触发 Reducer 更新 State |
| **PostReasoning** | 幻觉检测:验证输出与真实数据一致 |
| **OnSessionEnd/LiveEnd** | 记忆回写:提炼场景轨迹事件 |

**价值**:把"安全""可观测""持续演化"等横切关注点从业务逻辑彻底解耦,统一收敛到框架层。

## 四、沙箱执行防护:让"不可信代码"在隔离边界内运行

**核心原则**:任何 Shell/用户代码/第三方 Skill 脚本都按不可信对待。

| 维度 | 约束 |
|------|------|
| **身份与文件系统** | 非特权用户运行,根文件系统只读 |
| **资源配额** | CPU ≤50%,进程数 ≤64 |
| **网络** | 默认禁止出站,仅 allowlist 放行 |
| **系统调用** | 白名单收敛,禁用高危调用 |
| **环境隔离** | 不注入宿主机环境变量 |
| **执行约束** | timeout 只能缩小不能放大;stdout/stderr ≤64KB 截断 |
| **可观测** | 完整审计日志(代码+输出+user_id+session_id) |

## 五、五层安全防护体系:纵深防御

**设计原则**:前一层漏掉的由后一层兜底。

| 层级 | 机制 | 拦截风险 |
|------|------|---------|
| **第一层** | Prompt 边界硬编码 + Skill 定位声明 + 预校验 | 能力越界 |
| **第二层** | Schema 强约束 + 幂等性 | 非法参数/重复执行 |
| **第三层** | Approval 审批分层(auto/soft-gate/hard-gate/block) | 副作用操作风险 |
| **第四层** | 工具执行验证(业务方控制) | 业务规则违规 |
| **第五层** | 执行审计记录 | 事后追溯/争议处理 |

### 审批分层策略

| 风险等级 | 触发条件 | 审批方 | 策略 |
|---------|---------|--------|------|
| auto | 无副作用(查询/话术建议) | 系统 | 直接放行 |
| soft-gate | 有副作用但参数在安全阈值内 | Skill 定义规则 | 会话中提示用户 |
| hard-gate | 品类操作/批量操作 | 主播 | 阻塞等待二次确认 |
| block | 触发平台红线 | 框架 | 直接拒绝并告警 |

## 六、异常处理与降级策略

| 异常类型 | 检测方式 | 处理策略 |
|---------|---------|---------|
| 幻觉输出(编造商品) | 与实时数据交叉验证 | 拦截输出,提示人工确认 |
| 死循环(反复调用同一工具) | 相同工具+相似参数连续 ≥3 次 | 强制中断,告知主播并记录 |
| 响应超时 | — | 返回预设兜底话术,后台继续处理 |

## 七、LLM 驱动的 PlanEngine:从 ReAct 单步到 DAG 全局

**痛点**:复合指令(如"生成提案→创建直播间→同步商品→生成手卡→开启智能标题")用 ReAct 单步决策顾此失彼。

**升级**:从"逐步推理的局部最优"→"基于 DAG 的全局最优"。

### 五大建设目标

| 目标 | 实现 |
|------|------|
| **可恢复** | 三层 Checkpoint(每轮/每子任务/计划变更);断点续连 + 人工干预确认 |
| **可观测** | 三级状态可视化(Plan/SubTask/Tool Call),独立 TraceID 全链路追踪 |
| **提升执行效率** | DAG 无依赖子任务并行调度 |
| **提升执行成功率** | 全局最优规划 + 双重 Schema 校验 + 失败自动重试 + **增量 Replan**(只重规划受影响节点) + Token 预算控制 |
| **降低上下文漂移** | 执行进度外挂(不占 Context Window)+ SubAgent 上下文隔离 + Plan 快照持久化 + System-Hint 动态注入 |

**优化效果**:对比 ReAct,PlanEngine 在执行效率(冗余率/迭代轮次)和准确率(成功率/子任务覆盖率)全面占优。

## 八、评测体系:让质量可量化、可追踪

### 离线 + 在线双维度

| 维度 | 内容 |
|------|------|
| **Trace 分析** | 接入 Langfuse 可视化 trace |
| **离线评测** | 播前/播中/播后标注数据集 + **对抗样本**(极端改价/违规诱导/模糊指令)验证五层防护 |
| **在线评测** | 操作成功率 / 审批通过率 / 主播干预率 / 端到端延迟 |
| **主播满意度** | 每场直播结束打分(1-5 分),会话级主观质量信号 |

## 九、一句话总结

**主播 Agent 的 Harness 实践围绕八大能力展开:上下文工程(分层压缩+Reducer 状态+卸载)、工具调用(边界+Schema 幂等+错误码恢复)、生命周期 Hook(五时机拦截)、沙箱防护(隔离边界)、五层安全防护(Prompt→Schema→Approval→执行验证→审计)、异常降级(幻觉/死循环/超时)、PlanEngine(ReAct→DAG 全局规划,可恢复/可观测/并行/增量 Replan)、评测体系(离线+在线+满意度),让 Agent 在高风险直播场景"看得清、调得稳、防得住、规划远、测得准"。**
