# 更可靠的主播助理:淘宝主播 Agent 的 Harness 工程实战

> 核心命题:模型能力是概率的、会漂移的、偶尔会失控的,真正让 Agent 可用、可控、可演化的,是模型外面那一层工程化的"骨架"(Harness)。**模型会一代代变强,但包裹模型的这层 Harness 工程,才是把"能用的 Demo"变成"敢上线的产品"的真正壁垒。**

## 一、为什么主播 Agent 需要 Harness?

### 四大极端压力测试场

| 压力点 | 说明 |
|--------|------|
| **操作即时生效且面向公众** | Agent 下发指令错误无法撤回,代价是真金白银 |
| **主播注意力极度稀缺** | 主播在镜头前无余力逐条核验,安全边界必须由工程兜底 |
| **多话题高频交织** | 播前/中控/商品操作交替出现,上下文极易污染漂移 |
| **长程可中断要恢复** | 一场直播数小时,跨设备跨端切换,中断后必须精确续连 |

## 二、Harness 建设思想

### 2.1 Harness 六元组形式化定义

| 全称 | 职责 | 对抗的问题 |
|------|------|-----------|
| **Execution Loop** | 驱动"思考—行动—观察"主循环 | 失控(死循环/无限重试/跑飞) |
| **Tool Registry** | 定义工具能做什么、不能做什么、做错怎么反馈 | 能力边界模糊/参数非法/错误无法恢复 |
| **Context Manager** | 维护上下文的质量与体积 | 上下文膨胀/注意力漂移/信息退化 |
| **State Store** | 持久化运行状态,支持中断与恢复 | 长任务中断丢状态/不可回放 |
| **Lifecycle Hooks** | 在关键时机插入强规则拦截 | 模型不可控/强约束无法落地 |
| **Evaluation Interface** | 提供可观测、可分析的评估体系 | 质量不可量化/问题不可追溯 |

**水流理论**:人负责控制方向、设定边界与检查点,AI 负责在边界内自主推进。工程师建设的是"河道、闸门、护栏"——也就是 Harness。

### 2.2 三大设计思想

1. **框架层与业务层责任边界划干净** — 框架提供不变的工程能力(执行循环/上下文治理/安全防护/状态持久化/审计观测),业务方只写 Skill 声明能力
2. **安全是纵深防御,不是单点** — 从 Prompt 边界到执行审计的五层防御
3. **长程任务可恢复、可观测、可干预** — 三层 Checkpoint + DAG 全局规划

### 2.3 工程载体:逻辑统一、物理分治

| 资产类型 | 物理存储 | 选型理由 | 读写特征 |
|---------|---------|---------|---------|
| **会话信息** | MySQL | 强一致、点查高效、按 session_id/live_id 精确加载 | 在线频繁读写、状态持久化 |
| **记忆** | Hologres | 向量+全文+标量混合检索,多路召回 | 在线高频检索、异步写入 |
| **技能 Skill** | GitLab | 代码化维护、版本管理、Code Review、预检校验、灰度发布 | 离线维护、发布时加载 |

**两大收益**:① 负载分治,不用一套存储硬扛;② 统一工作区抽象屏蔽底层,业务只面向语义接口(加载上下文/读写记忆/调用技能/持久化状态)。

## 三、八项实战能力

### 3.1 上下文工程:看得清、记得住、不漂移

**对抗两堵墙**:上下文膨胀(Token 耗尽/延迟飙升/成本失控)+ 注意力漂移(关键信息淹没)。

| 手段 | 做法 | 价值 |
|------|------|------|
| **分层压缩** | 3 层压缩(历史工具调用/历史对话轮次/当前轮次)+ Session 级话题分段(打场景标签 pre-live/on-live/post-live) | 控制体积,保留可回溯结构 |
| **Reducer 模式** | LLM 只决策(产 Action),Reducer 纯函数变更 State;每轮把最新 State 快照注入 system-hint | 解决状态模糊/上下文膨胀/不可回放 |
| **大上下文卸载** | 大结果卸载到 OSS/Tair(路径 id + 预览);需提取→沙箱 shell 过滤,需摘要→工具返回 | 把"不必时刻在场"的内容外置 |

### 3.2 工具调用:能力边界、强约束与错误恢复

1. **能力边界声明** — Skill 注册时声明能力范围,调用前校验越权
2. **Schema 强约束 + 幂等设计** — JSON Schema 约束参数;有副作用写操作必带幂等键(UUID),框架层去重,杜绝"双切品""双改价"
3. **结构化错误码 + 自动修复**

| 错误码 | 类别 | 框架行为 |
|--------|------|---------|
| 3xxx | 业务异常 | 解析 AI 友好信息,换策略重试 |
| 4xxx | 参数异常 | 自动修复参数后重试 1 次 |
| 5xxx | 系统异常 | 自动重试,最多 3 次,指数退避 |
| 9xxx | 不可恢复异常 | 不重试,Hook 通知主播 |

### 3.3 生命周期 Hook:关键时机插入强规则

**哲学**:不改写模型推理循环,在关键时机插入钩子做拦截/注入/记录。

| Hook | 职责 |
|------|------|
| **PreReasoning** | 注入最新 State + 按需加载场景记忆 |
| **PreToolCall** | 安全拦截:能力边界/幂等键/风险等级审批 |
| **PostToolCall** | 结果校验 + 触发 Reducer 更新 State |
| **PostReasoning** | 幻觉检测:验证输出与真实数据一致 |
| **OnSessionEnd/LiveEnd** | 记忆回写:提炼场景轨迹事件 |

### 3.4 沙箱执行防护:不可信代码隔离

| 维度 | 约束 |
|------|------|
| 身份与文件系统 | 非特权用户运行,根文件系统只读 |
| 资源配额 | CPU ≤50%,进程数 ≤64 |
| 网络 | 默认禁止出站,仅 allowlist 放行 |
| 系统调用 | 白名单收敛,禁用高危调用 |
| 环境隔离 | 不注入宿主机环境变量 |
| 执行约束 | timeout 只能缩小不能放大;stdout/stderr ≤64KB 截断 |
| 可观测 | 完整审计日志(代码+输出+user_id+session_id) |

### 3.5 五层安全防护体系:纵深防御

| 层级 | 机制 | 拦截风险 |
|------|------|---------|
| 第一层 | Prompt 边界硬编码 + Skill 定位声明 + 预校验 | 能力越界 |
| 第二层 | Schema 强约束 + 幂等性 | 非法参数/重复执行 |
| 第三层 | Approval 审批分层(auto/soft-gate/hard-gate/block) | 副作用操作风险 |
| 第四层 | 工具执行验证(业务方控制) | 业务规则违规 |
| 第五层 | 执行审计记录 | 事后追溯/争议处理 |

**审批分层**:

| 风险等级 | 触发条件 | 审批方 | 策略 |
|---------|---------|--------|------|
| auto | 无副作用(查询/话术) | 系统 | 直接放行 |
| soft-gate | 有副作用但参数在安全阈值内 | Skill 定义规则 | 会话中提示用户 |
| hard-gate | 品类操作/批量操作 | 主播 | 阻塞等待二次确认 |
| block | 触发平台红线 | 框架 | 直接拒绝并告警 |

### 3.6 异常处理与降级策略

| 异常类型 | 检测方式 | 处理策略 |
|---------|---------|---------|
| 幻觉输出 | 与实时数据交叉验证 | 拦截输出,提示人工确认 |
| 死循环 | 相同工具+相似参数连续 ≥3 次 | 强制中断,告知主播并记录 |
| 响应超时 | — | 返回预设兜底话术,后台继续处理 |

### 3.7 LLM 驱动的 PlanEngine:ReAct 单步 → DAG 全局

**痛点**:复合指令(提案→创建直播间→同步商品→生成手卡→开启标题)用 ReAct 单步决策顾此失彼。

**五大建设目标**:

| 目标 | 实现 |
|------|------|
| **可恢复** | 三层 Checkpoint(每轮/每子任务/计划变更);断点续连 + 人工干预确认 |
| **可观测** | 三级状态可视化(Plan/SubTask/Tool Call),独立 TraceID 全链路追踪 |
| **提升执行效率** | DAG 无依赖子任务并行调度 |
| **提升执行成功率** | 全局最优规划 + 双重 Schema 校验 + 失败自动重试 + **增量 Replan**(只重规划受影响节点) + Token 预算控制 |
| **降低上下文漂移** | 执行进度外挂(不占 Context Window)+ SubAgent 上下文隔离 + Plan 快照持久化 + System-Hint 动态注入 |

**实测对比**(基模 qwen3.7-max,平均 7 步复杂任务):

| 对比项 | PlanEngine | ReAct |
|--------|-----------|-------|
| 执行成功率 | **0.847** | 0.737 |
| 子任务覆盖率 | **0.976** | 0.883 |
| 工具执行冗余率 | **0.587** | 0.727 |
| 迭代轮次 | **5.440** | 8.020 |

### 3.8 评测体系:让质量可量化、可追踪

| 维度 | 内容 |
|------|------|
| **Trace 分析** | 接入 Langfuse 可视化 trace |
| **离线评测** | 播前/播中/播后标注数据集 + **对抗样本**(极端改价/违规诱导/模糊指令)验证五层防护 |
| **在线评测** | 操作成功率 / 审批通过率 / 主播干预率 / 端到端延迟 |
| **主播满意度** | 每场直播结束打分(1-5 分) |

## 四、Harness 记忆:主播记忆可靠性提升

> 核心定位:不是简单套用通用记忆框架,而是被 Harness 工程思想深度重塑——与上下文管理(C)、状态存储(S)、Hook(L)、评估(V)紧密咬合。

### 4.1 与通用记忆系统的关键差异

| 维度 | 通用记忆系统 | 主播场景 |
|------|------------|---------|
| 短期记忆 | 多层压缩 | 多层压缩 + 会话场景信息摘要 + 结构化保存直播信息 |
| 时间粒度 | 对话轮次/按需触发 | 直播场次/事件驱动(对齐直播间生命周期) |
| 记忆分层 | 画像/经验/通用方法 | 主播画像 + 领域划分 + 事实决策路径 |
| 遗忘 | 时间衰减 + 矛盾覆盖 | 多因子加权衰减(场景相关性 + 新鲜度 + 时间 + 可信度) |

### 4.2 三层记忆模型:会话/事实/行为

| 层 | 性质 | 典型内容 |
|----|------|---------|
| **L1 会话记忆** | 主播主观声明 | 偏好("开场先上 100 以下引流款")、约束("X 品牌不能上")、反馈 |
| **L2 事实记忆** | 客观可查真相 | SKU 货盘/价格/券后/风控词/本场目标/时段/近 N 天曝光点击转化 |
| **L3 行为记忆** | 客观但需聚合归纳 | 主播行为模式(开场几分钟切款/主推讲多久)、粉丝画像 |

**分工**:L1 反映主播主观声明,L2/L3 负责客观信息补充和信任度评分。冷启动基于 L2/L3 历史数据推荐,随使用不断进化。

### 4.3 记忆对账与信任度进化

**核心洞察**:主播"说的"和"做的"不一定一致。

| 对账结果 | 示例 | 系统行为 |
|---------|------|---------|
| 一致 | L1 说"主推讲 10 分钟",L3 显示近 5 场均讲 10-12 分钟 | confidence 提升 |
| 矛盾 | L1 说"开场先上引流款",L3 显示近 3 场实际上了氛围款 | 记录 gap,不覆盖 L1,累积证据 |
| 矛盾累积 ≥3 次 | gap 证据充分 | Agent 主动提示主播确认是否更新偏好 |

**关键工程取舍**:矛盾时不粗暴覆盖,而是累积证据、达阈值后由 Agent 主动确认——既尊重主播主观意图,又让记忆基于客观事实进化。

### 信任度(trust_score)更新机制

基于 Decision Trace Log(问什么/Agent 答什么/主播选什么/最终效果),播后逐条归因更新:

| 事件 | Δ trust | 设计意图 |
|------|---------|---------|
| 采纳 + 效果好(lift>0) | +0.05 | 正循环 |
| 采纳 + 效果差(lift≤0) | −0.10 | 非对称惩罚:给错建议比不给更伤信任 |
| 拒绝 + 事后证明 Agent 对 | +0.03 | 慢慢建立"Agent 有时比我准"的认知 |
| 拒绝 + 事后证明主播对 | −0.05 | Agent 确实判断失误 |

### 信任度反向决定输出形态

| trust 区间 | 输出形态 |
|-----------|---------|
| ≥ 0.7 | 直接给 recommend:建议 + 反例 + 替代方案 + 把握度 |
| 0.4 ~ 0.7 | 给 evidence + 弱参考:数据摆出来,建议弱化为"供参考" |
| < 0.4 | 只给 evidence:纯数据,不给方向性建议 |

> **这套"Decision Trace + 信任度更新 + 输出形态自适应"的闭环,是主播 Agent 记忆体系的灵魂。**

### 4.4 直播场景多因子遗忘

采用多因子加权衰减(非通用时间衰减):

| 因子 | 说明 |
|------|------|
| **直播场景相关性** | 品类集中度、常播品类策略等 |
| **信息新鲜度分级** | 偏好/话术模板等经验型记忆慢衰减;价格/平台规则等波动型记忆快衰减 |
| **时间衰减** | 常规时间维度 |
| **可信度因子** | 已验证/高频使用记忆加成;被证伪记忆急剧降权;未验证保持基础衰减 |

配合定时清理(采纳次数/召回次数 ≤ 阈值则清理、超期清理)和记忆冲突处理(Last-Write-Wins + 自定义优先级,或召回时呈现给 Agent 主动确认),保证记忆库长期不失控、不腐坏。

## 五、一句话总结

**主播 Agent 的 Harness 工程用六元组 H=(E,T,C,S,L,V) 划清工程边界,用"业务写 Skill、框架兜底脏活"的分层解耦迭代效率与工程质量,用上下文工程(分层压缩+Reducer+卸载)、强约束工具调用(边界+Schema 幂等+错误码)、生命周期 Hook(五时机拦截)搭好通用底座,用五层纵深防御、DAG 全局规划(可恢复/可观测/并行/增量 Replan)、离在线评测扛住直播场景极端要求,最后用被 Harness 深度重塑的记忆体系(三层记忆+记忆对账+信任度自进化+多因子遗忘)让 Agent 真正做到"越用越懂主播"。**

> **模型会一代代变强,但包裹模型的这层 Harness 工程,才是把"能用的 Demo"变成"敢上线的产品"的真正壁垒。**
