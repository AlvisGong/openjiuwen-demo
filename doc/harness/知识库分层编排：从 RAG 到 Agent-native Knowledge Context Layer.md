# 知识库分层编排:从 RAG 到 Agent-native Knowledge Context Layer

> 核心命题:知识库的根本困境不是"没有内容",而是"缺少结构"。向量检索把知识当成"一袋词",而工程知识是"一棵树"和"一张图"。金字塔知识库补上了关键一环——**层次感知 + 角色适配**,让 AI 知道该去哪里找、按什么顺序读、给谁看哪些。

## 一、RAG 的天花板

### 三个结构性缺陷

| 缺陷 | 说明 | 来源 |
|------|------|------|
| **每次从零推导** | LLM 在每个问题上都从头重新发现知识,没有任何积累 | Karpathy: "the LLM is rediscovering knowledge from scratch on every question. There's no accumulation." |
| **无法连点成线** | 当答案需通过共享属性连接分散信息时,平坦向量检索无能为力;无法对大规模语料做全局语义理解 | Microsoft GraphRAG 研究 |
| **粒度混乱** | "设计原则"和"代码实现"在向量空间可能很近,但服务于完全不同的认知需求 | 向量空间不区分抽象层次 |

### 四个常见症状

| 症状 | 根源 |
|------|------|
| "搜什么都是那几篇" | 高词频长文档垄断 Top-K |
| "找到了但不是我要的层次" | 想知道"是什么",返回了"怎么实现" |
| "改了一个地方不知道影响什么" | 文档之间没有关联关系 |
| "新人不知道从哪看起" | 没有阅读路径和导航结构 |

**共同根源**:知识库缺少结构。

## 二、知识库方法论全景:四种范式

### 范式对比表

| 维度 | Naive RAG | LLM Wiki | Graphify | GraphRAG |
|------|-----------|---------|----------|---------|
| **知识表示** | 向量空间中的 chunk | 结构化 wiki 页面 | 有向图(节点+边) | 知识图谱+社区摘要 |
| **知识积累** | ❌ 无(每次从零推导) | ✅ 持续积累 | ✅ 增量更新 | 部分(需重建) |
| **知识关联** | 默认无(可加 metadata filter) | 手动 wikilink | ✅ 自动推断 | ✅ 自动推断 |
| **层次感知** | 默认无(可加 rerank) | 按主题分页 | 按社区分组 | 分层社区 |
| **角色适配** | 默认无(可加 ACL/query routing) | ❌ 无 | ❌ 无 | ❌ 无 |
| **适合规模** | 大(1000+篇) | 中(~100篇) | 大(整个代码库) | 大(但构建贵) |
| **维护成本** | 低(自动索引) | 中(LLM 维护) | 低(git hook 自动) | 高(需重建) |
| **核心能力** | 语义相似度检索 | 综合编译+导航 | 关联分析+缺口发现 | 全局理解+局部精确 |

### 各范式核心要点

**Naive RAG**:文档→chunk→embedding→向量数据库→相似度检索。简单但无积累/关联/层次/角色区分。

**LLM Wiki**(Karpathy):LLM 不只是检索者,是知识的维护者。三层架构(Raw Sources / Wiki / Schema)+ 三操作(Ingest / Query / Lint)。
- 核心洞察:wiki 是持续积累的工件
- 关键机制:好的回答反哺为新 wiki 页面,探索也成为知识积累
- 为什么不崩塌:LLM 显著降低维护瓶颈(摘要/交叉引用/归档/记账)
- 局限:wikilink 手动维护,无自动关系推断,适合中等规模(~100 文档)

**Graphify**:代码即图谱。双管道提取(AST 离线 + LLM 语义),三产出物(graph.html / GRAPH_REPORT.md / graph.json)。
- 独有能力:God Nodes(概念枢纽)/ Surprising Connections(跨模块关联)/ Knowledge Gaps(知识缺口)
- 置信度三档:EXTRACTED / INFERRED / AMBIGUOUS
- 局限:擅长关联分析,不擅长直接问答

**GraphRAG**(Microsoft):图谱增强检索。源文档→实体/关系提取→知识图谱→Leiden 算法社区聚类→分层社区摘要。
- 两种查询:Global Search(社区摘要做全局推理)/ Local Search(实体邻域)
- 解决 Naive RAG 的"连点成线"和"全局理解"两个痛点
- 局限:构建成本高(大量 LLM 调用)、增量更新困难

## 三、金字塔:新的知识工程范式

### 3.1 解决了什么

四种范式各有强项,但**都缺少层次感知 + 角色适配**。金字塔补上这一环:把知识按稳定性和抽象度分为 5 层。

### 3.2 五层分层设计

| 金字塔层 | 软件工程对应 | 稳定性 | 类比 |
|---------|------------|--------|------|
| **L1 原则** | SOLID / KISS / YAGNI | 最高(年) | 宪法 |
| **L2 架构** | 架构决策记录(ADR) | 高(季度) | 法律 |
| **L3 规范** | 编码标准(ESLint 规则) | 中(月) | 规章 |
| **L4 实现** | 代码模板、SDK 文档 | 低(周) | 手册 |
| **L5 经验** | 故障复盘、运维日志 | 最低(天) | 判例 |

**核心价值**:检索时先确定"用户在问哪个层次的问题",再在该层内精确定位——显著降低粒度混乱。

### 3.3 知识图谱:7 种有向边跨层关联

| 边类型 | 方向 | 含义 |
|--------|------|------|
| governs | L1→L2 | 原则约束架构决策 |
| defines | L1→L2/L3 | 概念定义域边界 |
| constrains | L2→L3 | 架构约束编码规范 |
| implements | L2/L3→L4 | 架构/规范的具体实现 |
| validates | L4→L5 | 实现产生运维经验 |
| feedback | L5→L3/L4 | 经验反馈改进规范和实现 |
| cross_ref | 任意 | 同层或跨层横向引用 |

支持四种图操作:上溯(实现→原则)/ 下探(原则→实现)/ 反馈环(经验→规范)/ 场景路径(预定义跨层阅读路径)。

### 3.4 角色感知:角色-层级访问矩阵

同一个知识库,架构师看 L1+L2,开发者看 L2+L3+L4。每个角色有独立的 `context_budget` 和 `priority_order`,系统按优先层顺序逐层填充直到预算用完——**确保有限 context window 里优先塞入该角色最需要的知识**。

### 3.5 检索机制:结构化路由 vs 向量相似度

**本质区别**:向量检索是"从所有文档中找最像的",金字塔是"先确定去哪层找,再精确定位"。

| 维度 | 向量检索 | 金字塔分层检索 |
|------|---------|--------------|
| 定位方式 | 语义相似度(embedding 距离) | 分层关键词打分 + 图谱扩展 |
| 搜索空间 | 全量文档 | 角色可访问层的子集 |
| 粒度控制 | 默认无(原则和代码混在一起) | 先按层过滤再定位 |
| 关联能力 | 默认单文档匹配 | 图谱边自动关联上下游 |
| API 调用 | 每次 1 次 embedding 调用 | **0 次(纯本地)** |
| Token 消耗 | 较高(返回 raw chunk) | 较低(budget 截断 + 摘要级) |
| 冷启动 | 无需预处理 | 需要先 ingest 构建金字塔 |
| 代码级深度 | ★★★★★(函数签名/行号) | ★★★(架构级,需穿透补深度) |

**最优组合**:金字塔做分层定位(0 API 调用)→ 向量检索补代码级深度(1 API 调用)= **结构化导航 + 精确细节的互补**。

### 3.6 与其他范式的关系

金字塔**不替代**其他范式,而是在顶层增加结构化的路由和导航层。金字塔 19 篇文档是 831 篇源文档的"索引+摘要+导航图"。

## 四、同步机制:知识库不是一次性的

### 4.1 腐烂的三种形式

| 类型 | 表现 | 危害程度 |
|------|------|---------|
| **静默过期** | 文档描述的接口签名已变,但文档没更新 | ★★★★★ |
| **层级漂移** | 当初的架构决策(L2)已降级为历史背景(L5),但还放在 L2 | ★★★ |
| **覆盖盲区** | 新服务上线 3 个月,L4 实现参考里完全没有它 | ★★★★ |

**判断标准**:如果团队新人按知识库操作后会踩坑,这篇文档就已经腐烂了。

### 4.2 知识保鲜三原则

**原则一:每层有不同的保鲜周期**

| 层 | 合理审查周期 | 过期信号 |
|----|------------|---------|
| L1 原则 | 年度 | 团队内部对某条原则产生分歧 |
| L2 架构 | 季度 | 系统拓扑图与文档不一致 |
| L3 规范 | 月度 | Lint 规则和文档描述不同 |
| L4 实现 | 周/天级 | 代码模板跑不通或依赖版本过期 |
| L5 经验 | 天级 | 故障排查 SOP 中命令/路径不存在 |

**原则二:用审计发现问题,而非人工巡检**

| 审计维度 | 检查什么 | 健康标准 |
|---------|---------|---------|
| 覆盖率 | 每层是否有条目、核心服务是否被覆盖 | 无空层,已知服务 100% 覆盖 |
| 新鲜度 | 条目最后更新时间 | 无超过 90 天未更新的 L4/L5 条目 |
| 图谱连通 | 是否存在孤立节点 | 所有条目至少有 1 条边 |
| 层级平衡 | 每层条目数是否合理 | L1 ≤ 10,无单层占比超过 50% |

**原则三:变更驱动更新,而非日历驱动**

| 触发事件 | 应更新的层 | 原因 |
|---------|----------|------|
| 架构评审通过 | L2 | 新的架构决策产生了 |
| Lint 规则变更 | L3 | 编码规范变了 |
| 依赖大版本升级 | L4 | 实现参考可能失效 |
| 故障复盘完成 | L5 | 新的经验知识产生 |
| 新服务上线 | L2 + L4 | 补架构描述和实现参考 |
| 新人入职提问 | L3 / L5 | 新人问到的问题说明文档有缺口 |

### 4.3 增量同步机制

**三阶段**:Phase 1 审计(扫描覆盖率/检测过期/输出 gaps)→ Phase 2 摄入(加载/分块/分类/去重)→ Phase 3 后审计(对比 Before/After 覆盖率改进)

**去重四策略**(checksum + entry ID 双重校验):

| 场景 | 动作 |
|------|------|
| 内容不变、同层 | skip |
| 内容变了、同层 | update(保留 createdAt) |
| 层级变了 | move(删旧写新) |
| 全新内容 | write |

## 五、测评结果

### 5.1 实验条件

- 知识库规模:831 篇源文档,14 个代码服务,5 个业务域
- 评测数据集:200 条 QA pair,覆盖 6 个维度,LLM 生成后人工审核
- 评测指标:RAGAS 标准(Hit@K / MRR / Context Precision / Context Recall / Faithfulness / Answer Relevancy)

### 5.2 六种测试模式

| 代号 | 模式 | 检索机制 | 类型 |
|------|------|---------|------|
| A | Naive RAG | 纯向量语义召回 | Vector Store |
| B | Pipeline Skill | 7 阶段 pipeline + 6 层路由 | Agentic Pipeline |
| C | Pyramid KB | 分层关键词 + 同义词扩展 + 图谱增强 | Hierarchical KB |
| D | Pyramid + RAG | Hybrid:金字塔路由 → 向量检索穿透 | Hybrid Retrieval |
| E | LLM Wiki | 23 篇编译 wiki + wikilink 导航 | Linked KB |
| F | Knowledge Graph | 86 节点 / 214 边图谱遍历 + 社区聚类 | KG Query |

### 5.3 检索指标结果(关键对比)

| 模式 | Hit@1 | Hit@3 | Hit@5 | MRR | Ctx Prec | Ctx Recall |
|------|-------|-------|-------|-----|----------|-----------|
| **D: Pyramid+RAG** | 89.0% | **89.5%** | 89.0% | **73.7%** | **0.636** | 0.580 |
| A: Naive RAG | 55.0% | 75.0% | 75.0% | 61.6% | 0.218 | 0.320 |
| F: Knowledge Graph | **64.5%** | 71.0% | 71.0% | 67.5% | 0.574 | 0.317 |
| C: Pyramid KB | 32.5% | 58.5% | 64.5% | 44.8% | 0.272 | 0.480 |
| B: Pipeline Skill | 44.5% | 54.5% | 54.5% | 49.3% | 0.419 | 0.457 |
| E: LLM Wiki | 31.0% | 40.0% | 40.0% | 35.4% | 0.242 | 0.400 |

### 5.4 分维度表现(Hit@3)

| 查询类型 | n | D:Pyr+RAG | C:Pyramid | B:Pipeline | F:Graphify | E:Wiki | A:RAG |
|---------|---|-----------|-----------|-----------|-----------|--------|-------|
| 代码细节 | 80 | **98.8%** | 87.5% | 61.3% | 75.0% | 66.3% | ~100%* |
| 运维排障 | 40 | **82.5%** | 47.5% | 17.5% | 67.5% | 22.5% | ~100%* |
| 架构概念 | 30 | 86.7% | 36.7% | 43.3% | **70.0%** | 23.3% | ~100%* |
| 跨服务关联 | 25 | 68.0% | 36.0% | **96.0%** | 92.0% | 4.0% | 0.0% |
| 导航 | 15 | **93.3%** | 40.0% | 46.7% | 33.3% | 33.3% | 0.0% |
| 服务定位 | 10 | 90.0% | 20.0% | **90.0%** | 60.0% | 50.0% | 0.0% |

### 5.5 局限性声明

- 单评估者(项目作者)、非盲评、评测集由 LLM 生成可能存在分布偏差
- 仅在单一团队知识库上测试,跨团队通用性需验证
- Mode A 数据为 8 条 API 实测样本估算值

## 六、一句话总结

**金字塔知识库从 RAG 进化到 Agent-native Knowledge Context Layer,核心是给知识加上"层次 + 角色 + 关联"三维结构。五层分层(L1 原则→L2 架构→L3 规范→L4 实现→L5 经验,对应宪法→法律→规章→手册→判例)+ 7 种有向边跨层关联(governs/defines/constrains/implements/validates/feedback/cross_ref)+ 角色访问矩阵(架构师看 L1+L2,开发者看 L2+L3+L4)+ 结构化路由检索(0 API 调用)+ 变更驱动同步机制,让 AI 能在 3 秒内返回正确层次、正确角色、正确关联的答案——而不是 5 段不相关的文本。实测 Pyramid+RAG 的 Hit@3=89.5% 显著优于 Naive RAG 的 75%。**

> **最终目标:程序员问一个问题,AI 能在 3 秒内返回正确层次、正确角色、正确关联的答案——而不是 5 段不相关的文本。**
